# Testing

Neither codebase has tests yet, and UdonSharp code only runs inside Unity, so tests can't run under a plain .NET test runner.

- A test behaviour, run in Unity Play Mode (with ClientSim), that executes checks and logs pass/fail.
- Perft counts from known positions (standard start, Kiwipete, Chess960 positions) against published values, which avoids depending on the Java. Perft also gives the speed numbers needed to judge the Udon performance concerns (see [Udon constraints](udon-constraints.md)). The deep perft in `RulesTest` (3.3a, 3.3b) takes a couple of minutes, so it sits behind the `deepPerft` Inspector tick. It only exercises move generation and make/unmake (`ChessMoves`, `ChessPosition`, `ChessRules`, and `ChessFen` parsing), so untick it for steps that don't touch those files and tick it again when they change. The shallow perft and move-count checks always run and still catch most move-generation regressions.
- Editor scripts (plain C#, not Udon) are tested by editor test scripts run from a menu item, logging pass/fail the same way, e.g. the empty-`SimpleAuth` build check: **Tools > Chess Board > Test Build Check** (6.3). The prefabs (step 14) are checked the same way by **Tools > Chess Board > Test Prefabs** (`Assets/Tests/Prefabs/Editor/PrefabTest.cs`), which drops each into a new scene of its own, opened beside the test scene and closed unsaved, and checks what it holds and how a change to it reaches instances. Since 14.2 it also checks the **Chess Board** (its own importer, arbiter and archive left to set, two placed with their own numbers and importers), that the open scene's boards are instances of it with their wiring, and that no prefab uses anything under `Assets/Tests/`; since 14.3 the **Chess Board View** (every object it uses wired to it, its pieces on their starting squares, no board or `I18n`, then pointed at a placed board) and that the open scene's views are instances of it, each on a board of its own; since 14.4 the **Chess Board UI** (its buttons, each action on its panels and each calling the placed UI's own event, its status panels, its PGN box hidden with both parts and its Import and Close, its sounds, no board, history wall or `I18n`, then pointed at a placed board) and that the open scene's UIs are instances of it, each on its own board with its board's history wall.; since 14.5 the **Game Archive** (its 10 synced holders and local-only recent holder its own children, each pointing back, a board pointed at it) and that the open scene's one archive is an instance of it with every board on it; and on every prefab, that each behaviour has the sync method its script asks for.
- **Networking needs real clients.** ClientSim runs a single local player, so ownership, sync and late joiners have to be tested with several clients, e.g. VRChat's Build & Test with multiple instances of the client.
- PGN import and export are tested with the PGN test set below, comparing against the Java (on `port-reference`) where the Java can read the file.

## Test behaviours

Every test behaviour (`RulesTest`, `PgnTest`, `SettingsTest`, `BoardTest`, `ViewTest`, `ArchiveTest`, `Board2DTest`) derives from `ChessTest` (`Assets/Tests/ChessTest.cs`, step 12.19), an abstract `ChessBoardListener` holding what they share: the pass and fail counts, `Check(ok, name, details)` logging `[<test>] PASS: <check>` or `[<test>] FAIL: <check>: <details>`, `UseEnglish(i18n)`, `Text(key)` and `TextWith(key, args)` (steps 13.5 and 13.5a: `SettingsTest`, `ViewTest`, `ArchiveTest` and `Board2DTest` hand `UseEnglish` the Chess Language, which it sets to English whatever the player's VRChat language, so the logs read alike; each text check names the key it expects and reads its text from there, `Text` through `ChessUtil.Text` and `TextWith` filling the `${name}` parts with `I18n.Format`, as the code does, with each test's short helpers building the composite lines (a status line, a wall row, a duration) from keys. So a check fails when the code shows a different key or fills a placeholder wrongly, not when a string in `en.json` changes. Only `ViewTest`'s language checks (13.5 below) write the English and test pack's text out, as they check the packs themselves), `CheckInt` and `CheckString` (details `got …, expected …`), `LogSummary` (the `[<test>] done: N passed, M failed` line, setting `finished`), `ReadyAfter` (for a test waiting for others: the local player joined and each test given finished, logging every 3000 frames that it still waits) and `NotationText`. Each test overrides `TestName()` with its name for the log lines. `PgnTest` keeps its own `CheckText`, which lays a multi-line PGN out on lines of its own, and `ViewTest`'s `CheckText` checks a square's object. Helpers alike only in purpose (`FindMove`, `Sq`, `StartGame`, `Play`) stay with their tests, as their code differs.

## One VR client

Only one VR headset is available, so a check may need at most one client in VR; every other client is on desktop. Checks written for VR players (pickups, carrying, snapping back, castling by drop) run on desktop clients through the view's `inputStyle` override, and are seen once more with the one VR client where the hand matters.

- **`inputStyle`** on `ChessBoardView` (step 9.2): **Auto** (the default: pickups in VR, clicks on desktop and mobile), **Pickups** or **Clicks** for every client. Desktop VRChat picks a `VRCPickup` up by clicking and holds it in front of the player, so with **Pickups** a desktop client exercises the same pickup and drop events, `pickupable` gating and ownership as a VR client. **Clicks** lets the one VR client try desktop mode.
- It's an Inspector field, so it's set before the build and is the same on every client of that build. A test needing both styles at once uses **Auto** with the one VR client, or two builds; the debug view also gets a button to cycle it locally (step 9.2), which needs no rebuild.
- A test is never written to need two clients in VR at once.

## Debug view

`ChessDebugView` (`Assets/Tests/Debug/`, PLAN 8.1) is a `ChessBoardListener` that shows a board as an 8×8 grid of pieces (FEN letters until 12.13, since then the 2D view's sprites; last move tinted, a checked king red) and its state as text, with a button for each of the board's input methods for the local player: join, mode, clock, start, scripted and random moves, resign, draw offers and claims, replay and stepping, takebacks, continuing, reset, and a few arbiter overrides with re-snapshot. It lets each client drive a board before `ChessBoardView` and the settings menu exist, and stays as a testing tool for networking checks.

- **Setup:** select the `ChessBoard`, then **Tools > Chess Board > Create Debug View**. This builds a world-space canvas (with `VRCUiShape`, so it works in ClientSim and VRChat) in front of the board, with each button calling the view's method of the same name through `UdonBehaviour.SendCustomEvent`. Move it if needed and save the scene. Running it again for a board that already has a debug view replaces that view in place (same parent, position, rotation and scale), so the scene picks up new buttons.
- Each button press logs `[ChessDebugView] <action>: accepted` or `REFUSED`, and an accepted one the board's state after it (lifecycle, seats, move count and last move, FEN, the result and ending once ended, the synced clocks as each side's stored ms and the turn start's server time, game ID, board owner). Each change of the board's owner is logged as `[ChessDebugView] board owner now <name> (was <name>), N players here` (8.8), so the logs show VRChat's handover when the owner leaves.
- **Sync** (8.3): each change arriving from another client is logged as `[ChessDebugView] received <change>: <the same state line>`, so comparing the clients' logs shows whether they agree; received notation holding a `null` entry is logged as an error. The text shows the board's owner and marks a received change.
- **Inactivity** (8.5): the ownership line shows how long the board has been idle, when reset becomes available and when the board resets itself (counted down, or "never"), and how many times this client has sent the board. **Fidget** picks up a piece of the side to move (any piece in replay) every half second for 30 s, putting it back, as a player handling pieces without moving, then logs `Fidget ended: N pickups, M activity stamps, K sends`; with the 5 s throttle that's about one send per 5 s from the side to move (none from anyone else outside replay), and the other clients log one `received activity` per send. Pressing it again stops it early. A reset after the auto-reset time is logged by the owner as `[ChessBoard] <board>: reset after N s idle` and arrives everywhere else as `received reset`.
- **Notation** (8.6): **Forget notation** blanks this client's notation of the game (every entry but every fourth, locally; nothing is sent), so the board fills it in over the next frames. The view then logs `[ChessDebugView] notation filled in: N entries so far, the last walk took F frames; the M entries before forgetting all match` (or how many differ, and the first). A received update with missing entries is logged as `received notation missing from ply P`, followed by the same `notation filled in` line. The move list shows a missing entry as `?`.
- **Import** (8.7): **Import PGN** imports the view's `importPgn` (Siggi-vs-Nuka, set by the builder) on the board, which loads and sends it when done; the text shows the import's status, and each change to it is logged as `[ChessDebugView] import <status> (<reason>); now <state line>`. The other clients log one `received loaded` with the 54 moves. **Import PGN (paused)** starts the same import but holds it (the importer's `paused` flag), so the board can be changed meanwhile, on this client or another, to see it abandoned (`import abandoned (the board changed before the import finished)`); **Resume import** lets a held import finish. The builder adds a `ChessPgnImporter` as a child of a board with no `importer`.
- `BoardTest` shares the board with the debug view, and its checks change the board, which is synced: it runs only when the local player is alone in the instance and logs `[BoardTest] skipped` otherwise, so a late joiner doesn't replace the game the others see. Its checks run over three frames (the step 7 checks; snapshots, listeners, scenarios, sync, ownership and inactivity; the notation fill-in and the import), each ending with the board reset: Udon halts a behaviour whose event runs past 10 s, and in VRChat all of them in one frame did (8.6). Then an import of Siggi-vs-Nuka runs over real frames on `BoardTest`'s importer (8.7), checked when it finishes (logged as `import timing:`), before the summary line.
- **Arbiter buttons** (8.2) change the arbiter as an organizer, through `BeginChange`/`EndChange`, so the change reaches every client; for anyone else they report `(not an organizer)`. Overrides for the board: takebacks, draw rules, clock forced to 3+2, clear. Instance defaults: takebacks, the reset-available time cycled through 30 s, 120 s and never, and the auto-reset time cycled through 60 s, 600 s and never (8.5; the arbiter keeps the reset-available time no longer than it). **Take arbiter** asks VRChat for ownership directly, skipping the organizer check, and reports the owner then and 3 s later, to see a non-organizer refused. **Take board** (8.4) does the same for the board, skipping the input methods' checks, to see a bystander refused while both players are here; the text shows whether both players are here, how long the board has been idle (and whether that's enough to reset) and whether the local player may take it. The text shows the arbiter's effective settings for the board, its defaults, its owner and the first joiner (with `FirstJoinerAuth`), and each change to them (made locally or arriving from another client) is logged as `[ChessDebugView] arbiter settings: …`.
- **Pieces** (9.2): the builder wires the debug view to the board's `ChessBoardView` (**Board View**). **Input style** cycles that view's `inputStyle` on this client only (Auto, Pickups, Clicks). **Take piece** asks VRChat for ownership of the first piece on the board directly, past `pickupable`, and reports the owner then and 3 s later, to see the piece's `OnOwnershipRequest` agree with the board (a refusal is also logged by the piece, as `[ChessPiece] <piece>: ownership refused for <name>`). The text's **Pieces** line shows the input style, whether this client is in VR and uses pickups, whether the board lets it touch the pieces and how many pieces are pickups for it; each change of that line is logged as `[ChessDebugView] pieces: …`.
- **Piece watch** (9.6): on every redraw the debug view compares each piece object with where this client's `ChessBoardView` puts it (`_ObjectPlace`: its square, its captured place, lifted when selected here, or the waiting promotion square), skipping objects still travelling. An object more than 0.05 squares off is logged once as `[ChessDebugView] piece <name> left its place (<square>): off by (x, y, z) squares, owner <name>[, held here][, selected here]`, and once back as `piece <name> in place (<square>) after T s away, furthest D squares; owner <name>`. The carrier's own client shows a held piece as `held here`; on other clients nothing but the view moves the pieces (no `VRCObjectSync` since 9.6), so a piece away from its place there is a fault. Two seconds after every board change but activity, each client logs `[ChessDebugView] pieces settled after <change>[ (received)]: all in place` or `N AWAY` with each one's state, the pieces' owners counted by name, the move count and the FEN: comparing the clients' lines shows whether the pieces end up where the board puts them everywhere. **Check pieces** logs the same line on demand, followed by `[ChessDebugView] places` with every object's place and owner, so clients' mappings can be compared object by object (a late joiner builds its mapping from scratch, so its objects may stand for other pieces than on the others, which is harmless now; with `VRCObjectSync` it pulled objects onto their owner's squares, the fault that removed it).
- **Archive** (10.1b): the text's **Archive** line shows the board's `GameArchive`: its games out of 50, its owner, how many holders are ready and who owns them, this client's recent games and how many of them aren't archived (`WAITING`), and `HELD`. Each change to it (a game archived here or a holder update arriving) or to its owner is logged as `[ChessDebugView] archive: <that line>; newest: #<sequence> <game ID> (<White> vs <Black>, <result>, N plies, continued from <ID>/<ply> when it was); …` (the newest three; every debug view in the scene logs it). The archive logs each game it archives (`[GameArchive] archived game …`, only ever on the owner) and becoming the owner (`GameArchive now owned here: N recent game(s) added`); a holder logs each ownership request it refuses. **Take holder** asks VRChat for ownership of holder 0 directly and reports its owner then and 3 s later, to see a non-owner refused. **Hold archive** stops this client archiving (`GameArchive.held`), so the games it logs wait in its recent games; on the owner, pressing it and then leaving is the owner leaving before it archived a game that just ended. Pressed again, it lets go and archives what waited. **Resign at :00** resigns for the local player at the next whole minute of server time (at least 3 s away), logging the server time it resigned at, so players on two boards end their games at the same moment; it says when the game has no moves yet, since such a game isn't logged or archived. (In 10.1b it was **Resign at :x0**, the next whole ten seconds; in 10.3 two presses about 2 s apart fell either side of the 3 s cutoff and resigned 10 s apart, so the window became a minute.) **Check archive** logs every archived game, oldest first, and this client's recent games. **Add 10 games** (10.3) hands the archive 10 random legal games from the standard start, one a frame, as a board logging them would (`Fill White <n>` vs `Fill Black <n>`, up to 80 plies, ended by checkmate or stalemate if one comes up, otherwise unfinished; no clock), logging each (`Add 10 games: <ID> (…) added, N to go`): on the archive's owner each is archived at once, so six presses fill the archive past 50 with games long enough to weigh on the late joiner's download; elsewhere they only wait in the recent games. A second board for that comes from **Tools > Chess Board > Create Board** (see [Architecture](architecture.md#more-boards)).
- **Played by `BoardTest`** (14.2): `BoardTest`'s `debugView` (set by **Create Debug View** for the test's board) is pressed through Join White, Join Black, Start, the fool's mate and Reset at the end of its third frame (`TestDebugView`), the board being the placed **Chess Board** prefab.
- **Piece sets** (13.6): the text's **Piece sets** line shows the board's synced indexes for White and Black, how many sets the arbiter lists, and this client's preferred set and override. **Preferred set** cycles the local player's `preferredPieceSet` through none and each listed set (the next join puts it on the board); **Override sets** cycles this client's override for both colours the same way. Test-only: no player UI of ours changes a board's sets.

## View test

`ViewTest` (`Assets/Tests/View/`, step 9) checks `ChessBoardView` against the board it shows, and since 12.1 the board's `ChessBoardUI` (`ui`): the buttons, status display and PGN box checks below go through the UI, the rest through the view, and the test brings both up to date where it checks straight after a change (`Redraw`: the view's `_Refresh`, then the UI's). ### Java exports and round trip

`java-export/<name>.java.pgn.txt` holds the Java's export (`PGN.serialize(PGN.deserialize(text))` on `port-reference`, written as UTF-8) of each file the Java can read. `PgnTest.TestRoundTrip` (5.4) imports each file, exports it as the board will export a loaded game (the tags the import keeps, Event/Site/Date unknown, the ending given by the test), and compares:

- **Moves:** read back with the port's reader, the SAN in the port's export and in the Java's are identical, `+`/`#` included. The Java's export also imports to the same moves and final position.
- **Comments:** the port writes only `{ [%clk …] }`, one per known clock, and the clocks read back are the file's. The Java's export keeps every comment (the test set's files have only clock comments) in the source's format, except that it **drops the comment after the last move** (its writer only writes comments before the next move), so its last ply has no clock.
- **Tags:** the tag lines differ by exactly the following (lines in both, in any order, aren't listed). Every file gets the port's `Event "?"`, `Site "?"`, `Date "????.??.??"` and `Round "-"` unless the Java has the same line (only Lichess's `Round "-"`). The port writes `TimeControl "?"` (unknown) for a file without the tag, and its own `Termination` values ([Game endings](game-endings.md)).

| File | Only in the Java's export | Only in the port's export (besides the roster lines above) |
|---|---|---|
| `Siggi-vs-Nuka` | `Site "VRChess"`, `Date "2025.7.10"`, `Termination "Nukaǃ won by checkmate"` | `Termination "checkmate"` |
| `lichess-long-draw` | `Event`, `Site`, `Date`, `_GameId`, `UTCDate`, `UTCTime`, `WhiteElo`, `BlackElo`, `WhiteRatingDiff`, `BlackRatingDiff`, `WhiteTitle`, `ECO`, `Opening` (none kept), `Variant "Standard"`, `TimeControl "60+0"`, `Termination "Normal"` | `TimeControl "60"`, `Termination "insufficient material"` |
| `en-passant`, `promotions`, `disambiguation`, `chess960` | nothing | `TimeControl "?"` |
| `stalemate` | `Termination "Draw by stalemate"` | `TimeControl "?"`, `Termination "stalemate"` |
| `repetition-names` | `Termination "Draw by threefold repetition"` | `TimeControl "?"`, `Termination "threefold repetition"` |
| `checkmate` | `Termination "Ana \"The Rook\" \\ Ñandú 🐴 won by checkmate"` | `TimeControl "?"`, `Termination "checkmate"` |

  The names (`"` and `\` escaped), `Result`, `GameID`, `Variant "Chess960"`, `SetUp` and `FEN` lines are identical.
- **Re-import:** importing the port's own export gives the same game: moves, recorded SAN, clocks (tenths kept, `-1` staying `-1`), starting position and numbering, final position, `White`, `Black`, `Result`, `FEN`, `GameID`, the mode and the time control (`60+0` and `60` both read as 60 s with no increment). This also runs for `formatting.pgn.txt` (whose clock history has `-1` entries) and a hand-written Chess960 game with escaped names, a `ContinuedFrom` and clocks with hours, tenths and unknown entries.
