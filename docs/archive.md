# Previous games: `GameArchive`, shown on the history wall

- Stores the games played in this instance: every game that gets logged (finished, or unfinished when reset or continued from an earlier position).
- Per game: game ID, continued-from reference, mode, time control, players, ending and winner, starting FEN, the packed move history and the per-move clock history.
- **No notation stored.** A game loaded from the archive starts with every notation entry empty, and the board's fill-in code ([Networking](networking.md#filling-in-missing-notation), time-budgeted) works it out over the next frames on every client: the loading player's and each one receiving the load. (Decided in 10.2b, replacing the loading player computing it and syncing it with the load: the fill-in already runs on every client, and nothing more is sent.)
- **Storage:** Udon can't sync arrays of arrays, so games are stored flattened: one `int[]` with every game's moves back to back, plus per-game arrays of IDs, names and numbers.
- **Capacity: 50 games**, in 10 **holders** of 5 games each. It's a circular log: once full, each new game overwrites the oldest. Reading the archive gives the games in chronological order (oldest first) whichever holder slot each sits in.
- **Bandwidth is the real constraint.** A manual-sync serialization sends *all* of a behaviour's synced fields, so with one behaviour holding every game, each game added would resend the whole archive. Split into holders, adding a game reserializes only the holder it goes into: 5 games of 80 plies are about 3 KB of moves and clocks. Late joiners still receive every holder, which is VRChat's job.

## One writer

- **One controller, `GameArchive`, and its holders, `GameArchiveHolder`.** Every board on every client hands each game it logs to its own client's `GameArchive` (each client logs each game once, on the transition; see [Game endings](game-endings.md)).
- **Only the archive's owner writes to the holders.** The archive object's owner is the instance's writer: when it's handed a game it isn't already holding (by game ID), it puts it in the next slot, takes ownership of that holder and serializes it. Every other client's copy of the same game is ignored, so the archive never gets two writers racing for a holder.
- **A holder may only be owned by the archive's owner:** its ownership request handler refuses anyone else, on every client. Nobody asks for the archive object itself (it refuses every request); VRChat hands it on when its owner leaves.
- **The recent games:** every client also keeps the last 5 games it logged in a local-only holder of its own, which never syncs. When a client becomes the archive's owner (the previous owner left, perhaps just as a game ended and before it was archived), it adds every recent game that isn't in the archive and that it has never seen in the archive. The same check runs whenever the owner is handed a game, and whenever a holder update arrives, so nothing is lost while the holders are still arriving. A client remembers which of its recent games it has seen archived (on its own client or in a holder update): once full, the archive overwrites its oldest games, and a recent game that was archived and then overwritten mustn't come back as the newest when that client becomes the owner. (Found in 10.3: after filling the archive, a client's overwritten recent games counted as waiting again.)
- **Readiness:** the owner only writes once every holder holds the instance's data: it has received the holder's state (late joiners get it on joining), or it has owned the holder since its start as the master (the instance's first player). Until then games wait in the recent holder.
- **Handover (step 10.1b):** VRChat hands a leaving player's objects to one remaining player, so the archive and the holders its owner held pass on together. The new owner archives its recent games that aren't in the archive (on `OnOwnershipTransferred`), taking ownership of each holder it writes, which the holders allow since it now owns the archive. A game the old owner archived reaches everyone before its leaving does; one it hadn't archived (it ended as the owner left) was logged by every client that had the game, the new owner included, and is in its recent games. A holder update can still arrive after the new owner wrote: if its write was refused, the arriving update replaces the holder, and the game, missing from it again, is archived again by the flush that every update triggers.

## Loading a game

- **Loading a game onto a board:** a player picks a game on the history wall. A "Load it here" button then appears on every board currently in its reset state, visible to that player; pressing one loads the game onto that board, which enters replay mode with it. The player who loaded it keeps the board until they join a seat (step 13.2, [Ownership](ownership.md)). No parsing is involved: the packed moves are copied straight from the archive. The players and result are shown the same way as for an imported PGN, and continuing from a position works the same way, including the `ContinuedFrom` reference.
- **A game can only be loaded onto a board in its reset state.** A board with a game in progress refuses. So does a board showing another loaded or imported game; it has to be reset first.

## Implementation

`Assets/Siggi/ChessBoard/GameArchive.cs` and `GameArchiveHolder.cs` (step 10.1a).

- **`GameArchiveHolder`** (manual sync): `Capacity` (5) slots. Each slot has a `sequences` entry (the order it was archived in, from 1; `0` for an empty slot, so the zeroed arrays are an empty holder), `gameIds`, `continuedFroms`, `whites`, `blacks`, `startFens`, and `InfoLength` ints in `infos` (mode, ending, winner, base time, increment, move count); `moves` and `clocks` hold the slots' moves back to back, in slot order. `WriteSlot` replaces one slot (rebuilding the flattened arrays), `SlotOf(gameId)` finds one, `MoveOffset`, `CopyMoves`, `CopyClocks` read one. As on the board, the state is packed into separate synced fields (`PackState`, from `OnPreSerialization`, writing `""` for a `null` string) and unpacked (`ReceiveState`, from `OnDeserialization`; an update that isn't valid is ignored), so a `localOnly` holder (the recent games) neither sends nor takes anything. `Send()` takes ownership and requests serialization (`sends` counts them, for tests). `OnOwnershipRequest` allows only the archive's owner, never for a local-only holder, and logs each refusal (`[GameArchiveHolder] Holder 0: ownership refused for <name>`); a `Send` that finds the holder still someone else's logs a warning and sends nothing. `ready` is set on the first update received, or on `Start` when the local player is the master and owns it (a late joiner can be reported as the owner of everything before the owners are known).
- **`GameArchive`** (manual sync, no synced fields: its ownership marks the writer): `holders` (10) and `recent` (the local-only holder). `AddGame(gameId, continuedFrom, white, black, mode, ending, winner, startFen, baseTime, increment, moves, clocks, count)` puts the game in `recent` (unless it's there already; a game with no ID or no moves is refused) and then calls `Flush()`, which, on the archive's owner with every holder ready, archives each recent game, oldest first, that no holder has and this client hasn't seen archived (`recentSeen`, per recent slot: set when a holder has the game, checked at the start of every `Flush` on every client, when this client archives it, or when it's stored already archived; cleared with the archive). `IsRecentWaiting(slot)` says whether a recent game still waits (the debug view's `WAITING`). Archiving gives a game the next sequence number (one more than the highest in the holders) and puts it in slot `sequence % Capacity` across the holders (holder `slot / 5`, entry `slot % 5`), so the 51st game overwrites the 1st. `OnOwnershipTransferred` to the local player and each holder update call `Flush()` too. Each game archived is logged (`[GameArchive] archived game <sequence>, <ID> (<White> vs <Black>), in Holder <h> slot <s>`), and so is becoming the owner (`[GameArchive] GameArchive now owned here: N recent game(s) added`), so only the owner's log has archived lines. `StoreRecent` is `AddGame` without the flush, for tests, and `held` (step 10.1b, for the debug view's **Hold archive**) stops this client archiving anything, as an owner that left before archiving.
- **Reading:** `GameCount()`, and per chronological index (0 the oldest): `GameIdAt`, `ContinuedFromAt`, `WhiteAt`, `BlackAt`, `StartFenAt`, `ModeAt`, `EndingAt`, `WinnerAt`, `BaseTimeAt`, `IncrementAt`, `MoveCountAt`, `SequenceAt`, `CopyMovesAt`, `CopyClocksAt`. The order is the holders' slots sorted by sequence, rebuilt after any change. `changes` counts changes, for views.
- **Boards:** `ChessBoard.archive`; `LogGame` hands the game to it with the board's ID, `ContinuedFrom`, seats, mode, the ending and winner logged, starting FEN, time control, moves and clocks.
- **Scene:** **Tools > Chess Board > Create Game Archive** builds the archive with its 10 holders and the recent holder as children, and sets every board's `archive`. Running it again replaces the archive in place.

### History wall (step 10.2a)

`Assets/Siggi/ChessBoard/GameHistoryWall.cs`, a view of the archive (no sync, no state of its own). It lists every archived game, oldest first, one row each: `#<sequence>  <White> vs <Black>: <ending> (<result>), <N> moves`, with `, Chess960` for that mode and `?` for a missing name, e.g. `#12  Ana vs Bo: White wins by checkmate (1-0), 12 moves`. The ending's words come from the language pack by `ChessGame.EndingKey(ending, winner)` (`ending_unfinished`, "Unfinished", for an unterminated game; `ending_time_forfeit_draw`, "Draw on time", for a drawn time forfeit; step 13.5), which `ChessBoardUI.EndingText` uses too; the row itself is `wall_row` (`wall_row_chess960`). The title reads `Previous games` (`Previous games: none yet` when empty). It redraws when the archive's `changes` count moves on (polled in `Update` by `RefreshIfChanged`), so a game archived on this client and a holder update arriving (a late joiner receiving the holders) both show.

- **Fields:** `archive`, `title`, `rows` (one TextMeshPro text, `TextMeshProUGUI`, per game the archive holds; a UI `Text` before 12.17); `Refresh`, `RefreshIfChanged`, `TitleText`, `RowText(index)`, `drawnChanges`.
- **Scene:** **Tools > Chess Board > Create History Wall** (`Editor/GameHistoryWallBuilder.cs`) builds a world-space canvas for the scene's only archive, 3 m wide, with 50 rows in two columns of 25 (oldest first down the left column, then the right), 2.5 m to the left of the leftmost board (along -x), level with the boards along z and facing them, so it's ahead and to the left from the spawn. Running it again replaces the wall in place (parent, position, rotation, scale).

### Loading a game (step 10.2b)

- **Picking:** each row of the wall is a UI Button (the canvas has `VRCUiShape` and a trigger collider, like the board's button panels) with a `GameHistoryRow` (`wall`, `index`), whose `Press` calls the wall's `SelectRow(index)`. That picks the row's game, by ID (`selectedGameId`, since a game's row moves once the archive is full), or unpicks it when it's the one picked; an empty row does nothing. The pick is the local player's alone (nothing synced), its row's text drawn in `selectedColor` (the rest in `rowColor`), and `selectionChanges` counts its changes. A picked game overwritten in the archive is unpicked when the wall redraws. `HasSelection()`, `SelectedIndex()` and `ClearSelection()` read and clear it.
- **Load it here:** a board button (`ChessBoardUI.ButtonLoadHere`, `PressLoadHere`; on `ChessBoardView` before 12.1), on both ends' panels next to the Join buttons, shown while `CanLoadGame()` (a reset board) and the UI's `historyWall` has a game picked. So it shows on every reset board, only to the player who picked. A UI brings its buttons up to date as soon as the wall's `selectionChanges` moves on (polled in `Update`). Pressing it calls `ChessBoard.LoadArchivedGame(gameId)` (the local player's form of `LoadArchivedGameAs(name, gameId)`, so the presser is recorded as `loadedBy`, step 13.2) and, once loaded, clears the pick, so the other boards stop offering it.
- **`ChessBoard.LoadArchivedGame(gameId)`:** refused unless `CanLoadGame()` and the board's `archive` holds the game (`GameArchive.IndexOf`). Copies the game's moves and clocks from the archive and passes them to `LoadGame` with empty notation, its starting FEN, mode, White and Black, its ending as a PGN result (`ChessPgn.ResultText`: `1-0`, `0-1`, `1/2-1/2` or `*`), its ID and time control. As for an import, the board then works the ending out again: a checkmate or stalemate from the position, otherwise `EndingUnknown` with the result's winner (an archived resignation shows as `Black wins`). Continuing it gets a `ContinuedFrom` naming it (`ContinueGameIdAt`).
- **Scene:** **Create History Wall** builds the row buttons and gives every board view on the archive's boards the wall; **Create Board View** gives a new view the wall too, and adds the button. Replacing a view points the behaviours that referred to the old one (`ViewTest`, debug views, `ArchiveTest`) at the new one, and replacing the wall does the same for the wall.
