# Bugs found in the Java

Fix these in the port. In the Java they're fixed on the `port-reference` branch of `JavaChessBoard/`, never on `main`, so comparisons against the Java (FEN, PGN or move-list output) are made on that branch and agree with the port. With these fixed, the Java matches the published perft counts for the standard start (depth 4), Kiwipete (depth 3) and perft positions 3 (depth 4), 4, 5 and 6 (depth 3).

- **Capturing a rook doesn't remove the opponent's castling right.** `MoveFinderPiece.findMove` only sets the removal flags for the *moving* piece, and `MoveFinderPawn` always passes `false`. Fixed by moves recording "removes the opponent's right" alongside the existing flags, for piece and pawn (promotion) captures.
- **Castling doesn't check the rook is there.** `MoveFinderKing.findCastleMove` checks the squares in between but never that the rook is still on its starting square, and `CastleMove` creates a rook of the castling colour on the destination. Combined with the bug above: after `Bxh8` capturing the rook, Black can still `O-O` and a rook appears on f8.
- **The castling path lets any king or rook stand in the way.** The same check allows any king on the rook's path and any rook on the king's path, of either colour, so e.g. White can `O-O-O` with another white rook on d1. Only the castling king and rook themselves may be on the paths. (Found while fixing the bug above.)
- **Castling doesn't remove the castling rights.** `MoveFinderKing` passes `!board.canCastleQueenSide(color)` / `!board.canCastleKingSide(color)` to `CastleMove`, which is inverted, so after `O-O` the FEN still shows `KQ` and the other side can castle later. (Found while fixing 1.6.)
- **Pawns can capture their own pieces.** `MoveFinderPawn.pawnAttack` accepts any occupied diagonal square without checking the colour, e.g. `cxd6` onto an own pawn. This made perft counts wrong (Kiwipete depth 1 gave 51 instead of 48). (Found while fixing 1.6.)
- **The halfmove clock never resets.** `Board.applyMove` adds 1 for every move, including captures and pawn moves, and `revertMove` subtracts 1, so FENs written after any capture or pawn move have the wrong halfmove clock (Siggi-vs-Nuka ended on `54` instead of `0`). Fixed by resetting it on captures and pawn moves; such moves store the clock they cleared (`Move.clearedHalfMoves()`, -1 for moves that don't reset it), so `revertMove` restores the old value. The port keeps the same per-move value in a local array alongside the move history, which each client computes rather than syncs (see [Move encoding](move-encoding.md#undo)). (Found while making the PGN test set.)
- **Tag values aren't escaped.** `PGN.writeTag` writes values raw, so a player name containing `"` gives a broken tag, and `TAG_PATTERN` (`\[(.*)\w*"(.*)"\]`) doesn't undo escapes. Fixed by escaping `\` and `"` on export (control characters become spaces) and reading values with a quote-aware pattern that undoes the escapes (see [PGN](pgn.md#player-names-in-tags)). (Found while making the PGN test set.)
- **Export numbers moves from 1 with White to move**, ignoring the starting FEN, so a game starting from `... b - - 3 40` came out as `1.gxh1=Q+ Kd2 2.…` instead of `40...gxh1=Q+ 41.Kd2`. Fixed by numbering from the starting position's side to move and move number. (Found while making the PGN test set.)

Not bugs, but differences on purpose: the port's PGN import is stricter than the Java's tokenizer, which silently skips text it doesn't recognise (including an unclosed `{`) and plays the moves in variations as if they were the main line. See [PGN](pgn.md#import-syntax). Comparisons against the Java therefore use PGNs without variations or unrecognised text.
